# Phase 4 initial analysis

The inspected application is an npm workspace: React 19.2/Vite 7.1/Tailwind 4 client, Express 5.1 API and better-sqlite3 12.4 database. Before Phase 4, all 67 backend tests and four real-browser tests passed on this Windows setup after correcting test teardown order. No applicable AGENTS.md, official problem-statement PDF, or existing recommendation module was found. The supplied Phase 4 prompt and verified implementation guide this work.

Routes and controllers delegate to services, which own immediate write transactions and deferred read transactions; repositories own SQL. Clients, venues, halls and bookings have foreign keys and interval/status constraints. Booking creation persists either CONFIRMED allocation or REJECTED reasons. Cancelled rows retain history. Atomic rescheduling excludes the original reservation, rolls back infeasible proposals, and supports stale-edit tokens.

Reusable `allocate`, `overlaps` and `peakUsage` are pure. Allocation tries the preferred venue, chooses the smallest capacity-eligible free hall, checks peak venue-wide resources, then uses deterministic fallback. `reservationInterval`, calendar validation and integer validation can normalize candidate requests. Existing API envelopes are `{data: ...}` and `{error: {code,message,details?}}`; booking creation uses POST /api/bookings, lifecycle uses PATCH routes, and availability uses POST /api/availability/check.

Plan: add a recommendation service with bounded calendar/grid generation, shared scheduling normalization, snapshot feasibility via allocate, lexicographic ranking, explanations and read-only API. Load confirmed reservations once for the search range. Add reusable React results/search controls on rejected details and failed reschedules. Selected alternatives use existing creation/rescheduling transactions with an exact-venue guard. A small additive confirmation-key table makes creation retries idempotent without changing rejected records. Thin routes/controllers and repository queries remain in their existing layers.

Modify services/index, lifecycle, routes, controllers, repository, schema, API client, booking detail, lifecycle actions and Phase label. Add recommendation service, selection guard, React recommendation component, tests and docs. No dependency additions are needed.

Risks: availability changes between preview and commit; fallback must not silently confirm a different selected venue; snapshot searches must never mutate; large candidate spaces must be bounded; calendar arithmetic must not convert civil times; duplicate retries need transactional protection. Reschedule preview must validate status/token before excluding an ID. Existing auth is absent and remains outside Phase 4. Relevant existing defects include detail refresh staleness and Windows SQLite cleanup ordering (already fixed locally). Unbounded general booking lists and startup inventory reseeding are outside this phase.
